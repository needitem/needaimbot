# bench — 조준 튜닝 하네스

일회성 실험 드라이버는 남기지 않는다. 결과는 커밋 메시지와 코드 주석에 적고
스크립트는 지운다 — 안 그러면 "이게 아직 유효한가"를 매번 다시 판단해야 한다.
남아있는 것은 **재사용되는 라이브러리 / 게이트 / 실측 도구**뿐이다.

## 컨트롤러 포트 (실행 코드의 손유지 사본)

| 파일 | 무엇 |
|---|---|
| `aim_sim_ring.py` | `needaimbot/cuda/pd_controller.cuh` 의 line-for-line 이식 |
| `aim_sim_select.py` | `simple_postprocess.cu` 의 타겟 선택 파이프라인 이식 |
| `aim_opt.py` | 위에 실측 노이즈·데드타임·클래스전환을 얹은 **현행 튜닝 하네스** |
| `realjit.py` | 실측 데드타임 분포(로그정규, 중앙 1.10프레임)로 돌리는 평가기 |
| `holdout.py` | 탐색에 안 쓴 seed 로 재평가 (과적합 검증) |
| `adaptive_deadtime.py` | 프레임별 적응 데드타임 실험 인프라 (`deadtime_adaptive`) |
| `ctrl_zoo.py` / `ctrl_zoo_opt.py` | 기각된 대안 컨트롤러(PID/Holt/KF-CA/게인스케줄) + 탐색 스캐폴딩 |
| `aim_alt_designs.py` | 기각된 대안 아키텍처 기록 |

**포트는 반드시 원본과 같은 숫자를 내야 한다.** `pd_controller.cuh` 나 `aim_opt.py`
를 건드렸으면 `parity/run_parity.sh` 를 돌릴 것 — 두 사본이 갈라지면 튜닝 결과가
통째로 무효가 된다.

## 게이트

- `parity/run_parity.sh` — 실제 device 함수를 결정론적 입력열에 돌려 프레임 단위로
  파이썬 모델과 비교. 8% 확률로 head↔body 를 뒤집어 클래스 전환 경로도 밟는다.

## 실측 도구 (리그에서 수집한 데이터를 읽는다)

| 파일 | 무엇 |
|---|---|
| `calibrate.py` | calib CSV → 검출기 σ / 결측률 / 프레임 타이밍 |
| `deadtime_fit.py` | emit→visible 데드타임을 **소수 프레임**까지 (`calibration_step_px>0` 필요) |
| `fps206.py` | 실측 프레임레이트로 물리 환산을 정정하고 데드타임 교차표로 검증 |
| `flatness.py` | 서로 다른 '최적점'들을 같은 조건에서 재평가 — 게인 표면이 평평한지 판정 |
| `deadtime_closedloop.py` | 주입 없이 emit 만으로 데드타임 추정 — **기각**, 아래 참조 |
| `w_robust.py` | 플랜트 데드타임을 흔들며 각 `w` 의 최악을 본다(감쇠 여유 선택용) |
| `crop_ab/` | 리그 프레임(`frames.npy`)으로 크롭·앵커·관측식 비교. `grab_frames.py` 로 재수집 |
| `plot_bottleneck.py` | `perf_stats.log` 병목 시각화 |
| `build_int8_engine.py` | INT8 엔진 빌드 (미사용 — 2026-08-01 기준 INT8 은 배제) |

`frames.npy` 와 원시 calib CSV 는 커밋하지 않는다(gitignore). 큐레이션한 표본만
`calib_rig_sample*.csv` 로 남긴다. 수집 모드는 `tools/measure.sh {deadtime|noise|off}` 로
켜고 끈다 — 손으로 진단 키를 토글하다 두 번 되돌리는 걸 놓쳤다.

## 하네스를 쓸 때 걸린 함정 (전부 실제로 겪음)

- **문서에 손으로 적은 값은 반드시 어긋난다.** `inference_pc/presets/README.md` 의 값
  표가 한 세대 뒤처져 있었다. 표는 데이터의 사본이므로 데이터에서 생성해야 한다
  (`tools/gen_preset_readme.py`, `preset.sh` 가 매 실행마다 호출).


- **탐색 seed 와 확정 seed 를 분리할 것.** 안 하면 노이즈 실현값에 맞춘 걸 실력으로
  착각한다. 제약 판정과 점수도 같은 seed 수로 재야 한다 — 다르면 현재 설정조차
  "제약 이탈" 로 나온다.
- **목적함수에 없는 것은 지켜지지 않는다.** 획득 속도를 제약으로만 걸었더니 근거리가
  4.2% 느려진 게 벌점 없이 통과했다.
- **측정 도구부터 검증할 것.** `deadtime_fit.py` 초기 구현에 정확히 -0.5 프레임 편향이
  있었다(차분 창 중심이 어긋남). 합성 정답으로 안 걸렀으면 그 값으로 설정을
  "고쳐서" 악화시켰을 것이다.

- **게인 목적함수는 평평하다 — 게인 재탐색은 하지 말 것.** `sigma_law.py` 가 노이즈
  레벨별로 낸 최적점 다섯 개는 서로 완전히 달랐다(`kp_x` 0.688~1.200, `soft_x`
  2.0~16.4, `mincut` 하한에 4회 고착). 그런데 `flatness.py` 로 **같은 조건에서** 전부
  평가하니 점수 폭이 **8.3%** 였다. 즉 최적점이 정해지지 않는다.
  이게 세션 내내 겪은 탐색 불일치의 원인이다 — 같은 제약에서 -1.3% 와 -3.0%, 14개
  값을 움직인 결과가 `max_step` 하나만 바꾼 것보다 나빴던 일, 240Hz 재최적화가 물리
  환산본보다 못했던 일. 전부 탐색이 매번 다른 구석에 착지한 것이지 개선이 아니었다.
  **σ 를 온라인 추정해 게인을 따라가게 만들 이유도 여기서 사라진다.** 추정기 자체는
  검증돼 있다(2차 차분 + MAD, 500프레임 ±8% / 순진한 std 는 ±89%) — 나중에 σ 가
  실제로 레버인 무언가가 나오면 그때 쓰면 된다.

- **실제로 통한 것은 전부 게인이 아니었다.** 적응 데드타임(지터 제거), 실측 데드타임
  반영(플랜트 모델 정정), 프레임레이트 물리 환산(단위 정합), `aim_h_ema`(관측식),
  공백 프레임 링 전진(버리던 정보). 공통점은 **모델을 실제에 맞추거나 버리던 정보를
  쓰는 것**이다. 이미 튜닝된 게인을 다시 짜낸 사례는 없다. 유일한 예외인 thumb
  프로필은 애초에 한 번도 최적화된 적이 없던 곳이었다.

- **어떻게 재느냐보다 무엇을 재느냐.** 프레임레이트를 하루에 세 번 틀렸다. 먼저
  중앙 간격(4.38ms→229)을 레이트로 읽었고, 그게 틀렸다는 걸 알고 **평균**으로 바꿔
  206 을 얻어 설정을 '정정'했다. 통계는 이번엔 맞았는데 **수집이 대표성이 없었다** —
  정지 표적 테스트였고 간격 표준편차가 1.61 이었다. 실전 플레이(클럭 고정, 401초)는
  **237fps · 표준편차 0.74**, 조준 중 231 이다. 결과적으로 '정정' 전 값(246 가정)이
  오히려 정답에 가까웠다(6% vs 12% 오차, 방향도 반대).
  통계량을 고른 뒤에 **그 데이터가 실사용 조건인지**를 물었어야 했다.
  실전에서 재보니 교전은 레이트를 거의 안 떨어뜨린다(238→231).
  → 레이트는 **플레이 수집의 조준 중 평균**으로 잡는다(`tools/measure.sh play`).

- **그런데 그 12% 오차의 대가가 사실상 없었다.** 실제 플랜트에서 네 후보(206/246/231
  환산 × w)의 총에러 폭이 **2.1%** 다. 위의 평탄성 결과 그대로다 — 환산비를 12%
  틀려도 게인 표면 위에서는 보이지 않는다. **진짜 레버는 `w`** 였다: 2.85→2.37 이
  획득 26.7→21.3ms(-20%), 오버슛 0.69→1.97. 게인 환산 오차와 `w` 과대추정이
  **서로 상쇄**돼 배포본이 우연히 프론티어 중간에 앉아 있다(획득 24.2, 오버슛 1.00).
  상쇄에 기대는 건 취약하므로 `w` 를 실측한 뒤 둘 다 정공법으로 맞출 것.

- **데드타임을 프레임으로 바꿀 때 어느 레이트에서 쟀는지 확인할 것.** 11.60ms 는
  143fps(`calib_step.csv`)에서 측정했는데 246fps 의 T 로 나눠 `w=2.85` 를 만들었다.
  측정값 중 캡처 샘플링분(≈T/2)은 레이트를 따라 줄고 나머지(USB + 게임 렌더)만
  남는다. ms 는 옮길 수 있어도 **프레임은 옮길 수 없다**.

- **데드타임은 플레이 중에 측정할 수 없다 — 맞히지 말고 견딜 것.** 주입 없이 컨트롤러
  자신의 emit 을 가진 신호로 쓰면 될 것 같지만 안 된다(`deadtime_closedloop.py`):
  주입으로 잰 진실이 1.66프레임인 143fps 수집 셋에서 3.10 / 4.85(탐색 상한) / 3.60 이
  나오고 **분할 절반끼리 2~3배로 어긋난다**. 폐루프라 입력이 표적 위치의 함수여서
  분리가 안 된다. 한 수집(206fps)에서만 2.80/2.75 로 깔끔했는데 그건 운이었고,
  하필 당시 설정값 2.85 와 가까워 편향과 구분도 안 됐다.
  → 대신 `w_robust.py` 로 **모르는 채로 버티는 값**을 고른다. 벌점이 비대칭이다:
  `w` 가 플랜트보다 낮으면 오버슈트가 터지고(16.97) 높으면 느려질 뿐이다(22→38ms).
  총에러 폭도 `w` 가 클수록 좁아진다(30.8%→14.3%). **`w` 는 맞히는 값이 아니라 감쇠
  다이얼이다** — 플랜트에 정확히 맞추는 게 과대보다 나쁠 수 있다(교차표에서 확인).
